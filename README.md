# E-commerce Medallion Pipeline (PySpark + Delta Lake)

An end-to-end data engineering project: raw, messy e-commerce order files go in, and clean, validated, business-ready tables come out, using the Bronze / Silver / Gold (medallion) pattern.

**Live results explorer:** https://areebaf29.github.io/ecommerce-medallion-pipeline/

> **Honest scope.** The data is synthetic and generated by `src/generate_data.py` (about 5k orders, with problems injected on purpose). The pipeline runs locally on PySpark 3.5 + Delta Lake 3.2. It was **not** run on Databricks. Bronze ingestion uses Spark Structured Streaming's file source with a checkpoint (`availableNow`), which behaves like Databricks Auto Loader for this purpose but is not Auto Loader. The live page shows saved results from a real local run; the pipeline does not run in the browser.

## Architecture

```
data/landing/*.csv  ->  BRONZE (raw, all strings + ingestion_ts + source_file)
                    ->  SILVER (typed, standardised, 6 rules) -> orders_valid | orders_rejected (+reasons)
                    ->  GOLD   (city, category, product, payment mode, delivered orders)
```

| Layer | What happens |
|---|---|
| Bronze | Incremental CSV ingestion with a checkpoint. Only new files are read on each run. Adds `ingestion_ts` and `source_file`. |
| Silver | Trims and standardises text, casts types, calculates `order_amount = qty * price * (1 - discount%)`, applies six validation rules, removes duplicate order IDs (keeps earliest ingested). Valid and rejected rows go to separate tables with a `rejection_reasons` column. |
| Gold | Revenue by city, category and product (delivered orders only), payment mode analysis (all valid orders, any status), a delivered-orders table (2,123 rows in the included run), plus reconciliation checks for each scope. |

### Validation rules
R1 city present, R2 quantity is a positive integer, R3 unit price > 0, R4 discount between 0 and 100, R5 order date is a real date, R6 payment mode is a known value. Duplicate order IDs are rejected as `DUP_duplicate_order_id`.

## Results from the included run
Run 1 used batch 1 only; run 2 added batch 2 (incremental). Final state:

| Bronze rows | Silver valid | Silver rejected | Delivered orders |
|---|---|---|---|
| 5,166 | 4,095 | 1,071 | 2,123 |

Delivered revenue reconciles across the city, category and product gold tables (INR 54,77,596.66). The payment mode table covers all valid orders of any status and is reconciled separately against that wider total. Run logs: `docs/run1.json`, `docs/run2.json`.

## Run it
```bash
pip install -r requirements.txt   # needs Java 11+ and internet on first run (Delta jar)
cd src
python generate_data.py ../data/landing
python run_pipeline.py --reset
python export_demo.py             # refreshes docs/data.json for the demo page
python -m pytest ../tests -q      # 6 Spark-backed tests (about 5 min on 1 core)
```
To see incremental ingestion, run the pipeline with only `orders_batch_1.csv` in `data/landing`, then add `orders_batch_2.csv` and run again.

## Tests
Six tests run real Spark jobs: each of the six rules fires with its own reason, null and malformed values are rejected without crashing, valid + rejected rows always equal bronze rows, re-running with no new files ingests nothing, a duplicate order ID arriving in a later batch is rejected (earliest copy kept), and the gold revenue tables count only delivered orders and reconcile to Silver, while the payment table reconciles to all valid orders. Writing these caught a real bug: a blank payment mode slipped through rule R6 (fixed).

## Limitations / next steps
- Synthetic data, single machine, no orchestration or scheduling.
- Port to Databricks (Auto Loader, Unity Catalog, Workflows) is a planned next step, not done.
- Rejected rows are not re-processed after a fix.
